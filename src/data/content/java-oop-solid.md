객체지향은 왜 절차지향과 다를까요? 그리고 "좋은 객체지향"의 기준은 무엇일까요. 네 기둥과 다섯 원칙(SOLID)으로 정리합니다.

## 객체지향의 네 기둥

- **추상화**: 복잡한 현실에서 핵심만 뽑아 모델로 만든다
- **캡슐화**: 데이터와 메서드를 묶고 private으로 보호한다
- **상속**: 공통을 부모로 올려 재사용한다
- **다형성**: 같은 호출에 객체마다 다르게 반응한다

이 넷에서 재사용성(상속), 유지보수성(캡슐화), 확장성(다형성)이라는 장점이 나옵니다.

## SOLID 다섯 원칙

| 원칙 | 한 줄 요약 |
| --- | --- |
| SRP | 클래스는 변경 이유가 하나여야 한다 |
| OCP | 확장엔 열고 수정엔 닫는다 |
| LSP | 자식이 부모를 대체해도 깨지지 않는다 |
| ISP | 안 쓰는 메서드까지 떠안기지 않게 인터페이스를 잘게 |
| DIP | 구체가 아니라 추상에 의존한다 |

**LSP** 가 와닿는 예가 있어요. 날지 못하는 펭귄을 "나는 새"(Bird.fly)로 상속시키면, 부모 자리에 펭귄을 넣는 순간 깨집니다. 그래서 fly는 `Flyable` 인터페이스로 분리하는 게 맞아요.

## 못 지킬 수도 있다, 설명할 수 있으면 된다

SOLID는 이상적 목표입니다. 작은 프로젝트에 다 적용하면 오히려 불필요한 복잡성이고, 레거시나 촉박한 마감에선 못 지키기도 해요. 면접에서 진짜 보는 건 원칙 암기가 아니라 **"왜 못 지켰는지 설명할 수 있는 설계 감각"** 입니다.

<div class="callout callout-tip"><span class="callout-label">KEY POINT</span><b>DIP</b>는 사이트의 "좋아요는 왜 likeCount++로 끝나면 안 될까" 글에서 다룬 의존성 역전과 같은 원칙입니다. 거기선 아키텍처 레이어 방향(Repository 인터페이스는 도메인에, 구현은 인프라에)으로 풀었고, 여기선 언어 기능으로 본 것이에요. 두 관점을 같이 보면 입체적으로 잡힙니다.</div>
